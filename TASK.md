# Milestone 10 — Kubernetes Deployment

Что уже есть:
1. k3s кластер, `traefik` заменен на ingress-nginx контроллер
2. Всего на вм-ке 4 гига озу, 30 гигов пзу, 2 vcpu.

### Что нужно будет добавить (просто список, инструкции ниже):

1. Workloads кубера:
	1. Deployment — главный манифест, который описывать pod, который должен постоянно работать. Здесь указываются энвы, пробы, почти все, что нужно приложению.
	2. K8s Job — это вещь, которая должна один раз сработать и закрыться. Для init-db.
	3. Ingress — нужен, чтобы кластер был доступен извне по хостам `88-218-67-241.sslip.io` и `auth.88-218-67-241.sslip.io`. ingress-nginx контроллер уже открыл нужные порты (80, 443), ингрессы помогут донастроить доступность извне.
	4. CertManager — возьмет на себя работу с сертификатами.
2. Манифесты кубера:
	1. `ClusterIP` (чтобы работали урлы вида `postgres:5432`)
	2. `PersistenceVolumeClaim` (заменяет docker volumes)
	3. `ConfigMap` — не секретные env-ики и тот json для кейклока
	4. `Secret` — для секретных env-иков
	5. `ClusterIssuer` — идет в паре с CertManager (см п.1.4.) нужен для управления сертами, ingress-ы и keycloak будут обращаться к нему

### Теперь по порядку

1. Добавь CertManager. Вот инструкции (дочитай пункт до конца): [раз](https://kubernetes.recipes/recipes/security/kubernetes-letsencrypt-ingress-cert-manager/) и [два](https://cert-manager.io/docs/tutorials/acme/nginx-ingress/). Первая короткая, все по делу. Вторая более развернутая, с официального сайта cert manager, там есть дополнительные шаги по развертыванию тестового приложения, а также описывается разница между `Issuer` и `ClusterIssuer`. Создай `ClusterIssuer`, используй `staging`-версию letsencrypt-а. Ингресс можешь создать сразу, можешь пропустить, энивей мы вернемся к нему в пункте 9.

2. Создай namespace `tech-support`.

3. Создай `Secret`-ы. Три секрета: postgres-secret, keycloak-secret, backend-secret. Я предлагаю не дублировать проперти, вместо этого поместить DB_USER/PASSWORD в postgres-secret, и маунтить его в бэкэнд. Аналогично с кейклоком. `JWT_SECRET`, `PASSWORD_PEPPER`, `OIDC_CLIENT_SECRET` логически не подходят к этим двум сервисам, поэтому их в backend-secret. Тут (и дальше) ссылку на инструкции прикреплять не буду, т.к. популярный вид манифеста, поэтому одним запросом сможешь все найти.)

4. Создай `ConfigMap`-ы. Две штуки: одна для бэка с несекретными энвами, вторая для кейклока с realm json-ом. Вроде там принято использовать формат `ENV_KEY=VALUE`, но тут без жестких ограничений — используй тот формат, который больше хочешь.

5. Postgres. Здесь и дальше мы по сути пытаемся перевести настройки из docker compose на язык кубера. Понадобятся `Deployment`, `ClusterIP` сервис (`postgres`, порт 5432), и `PersistenceVolumeClaim` под `/var/lib/postgresql/data` на замену тому docker volume. Добавь readiness пробу с вызовом `pg_isready`, прямо как у тебя в healthcheck.

> На вм-ке ресурсы достаточно ограничены, поэтому ставь по одной реплике, а еще каждому деплойменту указывай обязательно `resources.requests`/`resources.limits`. По значениям: ~100-150 МиБ для фронта, ~300-400 МиБ для постгреса, ~600-800 МиБ для бэка и кейклока. Проверять, кто сколько по факту использует, можно с помощью `kubectl top pods`.

6. Создай Keycloak. `Deployment`, `ClusterIP` (порт 8080 и 9000 для хелсчека), `PersistenceVolumeClaim`, `ConfigMap` с тем realm json-ом. По-прежнему делаем `strat-dev --import-realm`, те же энвики. Хелсчек переносим в readiness пробу.

7. Создай Backend. `Deployment`, `ClusterIP` (порт 8080). Подключи `Secret`-ы и ту `ConfigMap`. Проверь, что урлы в бд и кейклок указаны верно. Добавь readiness пробу, которая будет пинговать `/actuator/health`.

8. Frontend. Нужно убрать из `nginx.conf` логику по обработке сертификатов. Нужны будут `Deployment`, `ClusterIP` (порт 80 внутри, публиковать порты больше не нужно, т.к. за это отвечают ингрессы). Вольюмы для сертов не нужны, это переедет в CertManager на следующем пункте.

9. Создай один ингресс с двумя правилами: `88-...ip.io` -> frontend Service, и `auth.88-...ip.io` -> keycloak Service. Каждому правилу понадобится `tls` блок — в нем нужно указать Secret, который будет заполнен cert-manager-ом. Также в ингресс нужно добавить аннотацию `cert-manager.io/cluster-issuer`, которая укажет на наш `ClusterIssuer`.

10. (опционально) Для init-db можно создать либо `initContainer`, прикрепленный к backend Деплойменту, либо оформить это как Kubernetes Job. Этот выбор оставлю тебе, можешь глянуть, в чем их особенности, как эти вещи настраивать, и решить, нужно ли это в целом, или хочется оставить это без автоматизации на уровне кубера, и делать старым добрым ручным курлом. :)

11. По идее все развернуто, можно проверять, кидать запросы, и дебажить.

### Как понять, что все готово

`kubectl get all -n tech-support` — все деплойменты `1/1 Ready`. Если создавала job/initContainer для init-db, он дб в статусе Completed. Запросы по хостам возвращают контент, HTTPS работает, логин работает как по username-password, так и по SSO.
